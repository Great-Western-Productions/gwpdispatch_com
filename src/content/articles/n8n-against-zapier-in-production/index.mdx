The pitch for a hosted automation tool is that a workflow is a form. Pick a trigger, pick an action, map the fields, done. Zapier built that market and still sets the expectation. n8n sells the same picture with a cheaper per-execution bill and a source-available core under its Sustainable Use License. After most of a year running n8n Cloud in production for a small operation, the picture is a poor guide to the choice. The difference is what happens on the day the form is no longer enough.

That day arrives early. A weekly research job scores keyword candidates against a scoring model: a few hundred lines of logic with test fixtures. Zapier offers a code step, and so does n8n, but the comparison is everything around the code step. n8n's Python option blocks standard-library imports, so the scoring core became a JavaScript port, parity-tested against the Python reference. The port lives in a repository, is read into the workflow at run time, and runs inside the Code node. A second workflow, a nightly sync between two databases, goes further. Its diff logic is a pure function with `node --test` fixtures, a build script injects it into the Code node, the workflow definition is a JSON file in the repo, and a drift check compares the live instance against the build. Those are software engineering habits. Zapier's model has no place to put them. The live zap is the definition of record. Some plans export a zap as JSON, but the export is a snapshot with no build or drift check behind it.

Credentials are the second place the tools diverge. One workflow calls a research tool on a home server. n8n Cloud cannot reach a LAN address, so the tool went behind a Cloudflare Tunnel and an Access policy with a service token, held in n8n as a header credential. The HTTP Request node could not apply a credential carrying two headers; the MCP Client node could. That is an hour lost to a platform quirk, one that can be worked around in the open, because the node catalog and its limits are documented. On a closed platform the same wall is a support ticket.

Replay is where the honest comparison lands. n8n keeps each execution's node outputs, but a run that spends money against a metered API cannot be replayed from raw responses unless the workflow stored them. These runs did not, so a mis-scored candidate means a paid re-run. The laptop version of the same pipeline, plain Python, keeps raw responses and replays for free. Capture is a design decision inside the workflow, in either tool, and it has to be made on purpose.

Duplicate protection is the same story. A GitHub file-create node fails with HTTP 422 when the file exists. A second same-day run of the research job did that, after the review task and the digest email had gone out. The guards were added by hand afterward: a dry-run flag, a ceiling on the number of changes, a daily schedule with no polling trigger, and an error workflow that catches failures. On Zapier those guards are whatever the platform offers, because there is no file to add them to.

The choice follows from that. Zapier fits an operator who wants connectors and does not expect to open a code step. n8n fits an operator who has a repository, a test runner, and someone who reads a JSON diff. The price difference is real and secondary. The wrong tool is the one whose failure mode the operator cannot inspect.
